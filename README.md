# 四级作文批改

一个 CET-4 作文批改网站。给档次、给分数、给证据溯源、给升档建议（每条都配「改哪句、改成什么」的示范），
最后给一段「这类毛病平时怎么练」的训练区，能下载一份自包含的 HTML 批改报告。
批改是流式的：报告在输入页上边生成边填出来，分数作为收尾出现，一出现就是终值。

## 快速开始

```bash
npm install
cp .env.local.example .env.local   # Windows: copy .env.local.example .env.local
# 编辑 .env.local，填入 DEEPSEEK_API_KEY 和 REVIEW_ACCESS_CODE
npm run dev
```

本地开发就到这里。想把限流做成真的（而不是单实例内存里的减速带），再多两步：
去 neon.tech 建个库，把连接串填进 `.env.local` 的 `DATABASE_URL`，然后跑
`npm run db:init` 建表。不配也能跑，页面会提示你限流没生效。

打开 http://localhost:3000 是**开播页**（那个玩笑页），点「真开播了！」进 `/access` 输口令，
验过了才会到 `/review` 开始批改。没配 key 的话页面顶部会直接提示，不会让你写完作文才报错。

想先看看效果，输入页有三个内置示例作文（低/中/高三档），点一下就能填进去。


（自测的项数不写在这里了。它每次改动都会坏，而坏掉的方式是"数字过时"而不是"测试失败"，
没有任何东西会提醒你。）

⚠️ `npm run build` 和 `npm run dev` **不能同时跑**：两个都往 `.next` 里写，先起的那个会被
后起的那个写坏，症状是页面 500 且报 `__webpack_modules__[moduleId] is not a function`。
`db:walkthrough` 又需要一个跑着的 dev server，所以正确顺序是：**停 dev → build →
删掉 `.next` → 再起 dev**。删这一步不能省：留着生产构建的 `.next` 直接起 dev，
就是上面那个 500。

`npm run selftest` 覆盖了证据定位（含**歧义判定**与未定位）、档次查表、分数折算、
`score15` 入口的收拢（模型给字符串/布尔/越界值时的每一种下场）、`kind` 兜底、
高亮切分与锚点映射、HTML 转义（XSS）、**导出报告的零 JS 约束**（没有 `<script`、
没有内联事件处理器、没有外链）、模型输出的防御性解析、请求体大小上限、限流策略与口令锁定、
限流 SQL 的**文本性质**、`!res.ok` 时的上游错误码与读 body 超时、
客户端断开时中止上游调用、SSE 分帧（含帧被切在两块 chunk 之间）、
增量 JSON 扫描的前缀单调性、流式与非流式对同一份模型输出的完全一致、
客户端看门狗的两个阈值与提示边界、草稿收拢与报告新鲜度判定、
两条路由共用的口令处置（`humanizeWait` 的取整方向、`penalizeAccessFailure` 的拖慢与
"失败记在哪个 key 上"），以及一条 mock 掉模型调用的端到端流程。改完代码先跑它。

它测不到屏幕上的东西——**这个项目刻意没有前端测试框架**。所以取向是「凡能抽成纯函数的
逻辑都抽出来」：`lib/watchdog.ts`、`lib/rubric.ts` 的 `readScore15`、`lib/store.ts` 的
`coerceDraft`/`isResultFresh`、`lib/review.ts` 的 `coerceKind` 都是这么来的，
抽出来就能在这里断言，留在组件里就一行都测不了。

**它测不到限流 SQL 的实际行为**——那是离线的，只有纯函数和 SQL 文本。CASE 分支实际走
哪一条、`LEAST` 有没有真的夹住、衰减谓词在真库上是什么效果，只存在于数据库的求值结果里。
那部分由 `npm run db:smoke` 覆盖（手动跑，需要真实数据库）。

还有一层是上面两个都够不到的：**路由怎么把这些结果翻译成 HTTP**。比如"失败刚好把人锁上"
时返回的是 429 而不是 401、锁定期内的请求在读 body 之前就被拒因而不计数、口令正确也穿不透
硬锁、第 100 次放行而第 101 次是 429、以及口令页（`/api/access`）和批改走的是**同一条**
防爆破路径但它不占额度——这些只有打真实 HTTP 才看得见，由
`npm run db:walkthrough` 覆盖（需要 dev server 已经在跑；它用短作文穿过闸门，不会真的
调用模型）。改限流顺序或状态码时**三个都要跑**。

`db:walkthrough` 是本机专用的：它靠 `client_key = "::1"` 去核对库里的行，跑在 Vercel 上
那个 key 会是你的真实出口 IP，库里那些断言会全部落空。线上验证见「部署后验证」。

它开头会先空转几圈把数据库**焐热**再开始断言（会打一句「预热了 N 次才快起来」）。
这一步不能省：Neon 的冷连接第一次查询能越过 `lib/db.ts` 那个 4 秒超时，撞上的那一次
请求会被判成"数据库不可用"而**降级到内存实现**——限流那一刻是真的漏了，而脚本这边
看到的是一串看起来像"策略坏了"的红（第 7 次失败没锁上、库里的计数停在 6……）。
只预热、不掩盖：真降级了照样会红，因为每一轮都读库核对。

## 访问口令

`POST /api/review` 烧的是站长自己的模型额度，所以加了一道共享口令：请求必须带上与服务端
`REVIEW_ACCESS_CODE` 一致的口令才能批改。

**没配 `REVIEW_ACCESS_CODE` 时，服务端拒绝一切批改请求**，不会静默放行。这是刻意的——
公开站点上「忘了配所以裸奔」的代价太大，宁可让它坏得明显。输入页会在这种情况下提前提示，
而不是让你写完作文才报错。

口令**在进门那一步就验掉**：首页那个按钮落在 `/access`（口令页），验过了才跳到 `/review`。
不这么做的话，输错口令也能进批改页，要等写完一整篇点下「开始批改」才发现——而那次尝试
**已经计进配额了**（口径是"口令通过的请求"，见下面「计数口径」），一次额度加一篇作文一起白花。
输入页顶部仍然留着口令框，因为口令可能在你停留期间过期（站长轮换了），那时不必回到门口。

验口令走的是 `POST /api/access`。它不碰模型、不占那每小时 100 次的额度，**但防爆破的待遇
和批改一模一样**：错口令记失败、按档位上锁、每次失败多等 400ms。这条不能松——它不花钱、
看起来人畜无害，于是最容易被当成"另一个入口"，一旦比 `/api/review` 宽松一点点，
爆破的人就改从这里进。两处共用的处置和文案在 `lib/access-gate.ts`，不在路由里各写一遍。

口令在 `/access` 输一次后记在浏览器 localStorage 里，之后免输（再进 `/access` 会自动验一次
然后直接送你过去）。只有口令**正确**时才会被记住，输错不会被持久化，免得下次预填一个错的值。

轮换口令：改环境变量（线上改 Vercel 的环境变量）然后重启 / 重新部署，不需要改代码。
口令请用长随机串。下面那些限流是辅助：它们按 IP 归并，同一个出口 IP 下的人会互相连累，
而口令泄露之后限流拦不住泄露的那一方——真正的第一道防线仍然是口令本身有足够的熵。

校验在路由层（`app/api/review/route.ts` 和 `app/api/access/route.ts` 各一处），核心逻辑是
`lib/access.ts` 里的纯函数，比对用 `timingSafeEqual`（先各自 SHA-256 摘要再比，
避免长度不等时抛错，也不泄露口令长度）。

两条路由有两处**有意**的不同，都是"口令页不花钱"这一个事实带来的：口令页**不做配额早拒**
（它没让站长花一分钱），**而且口令验对了也不清零失败计数**（清零是 `recordSuccess` 的副产物，
而它的语义是"批改了一次"，借用它会顺带吃掉一次额度）。代价是"在口令页连错 6 次、
第 7 次输对"之后再错一次就会被锁——刻意的取舍，要清零就得在存储层加一个"只清失败、
不计数"的方法（Postgres 和内存两份实现都要写，自测也要跟着加），换来的只是少一次误锁。
正常路径不受影响：接着批改一次，那条写语句会把失败记录一起清零。

## 限流的真实边界

限流的状态**存在 Neon Postgres 里**（`rate_limits` 表，一个客户端 IP 一行），
不是存在进程内存里。这是为了在 Vercel 这种无服务器环境里真的生效：每个实例有独立的
进程内存、实例随时回收也会横向扩容，计数放在内存里的话，并发请求分散到不同实例就
各记各的，实际允许的次数按实例数成倍放大。

改成外部存储之后，这些限制**跨实例共享**，是一堵真的墙。代价是一整套新的失效模式，
按危险程度排在下面。

### 规则

规则写死在 `lib/rate-limit.ts` 里，**不是环境变量**。这样"两个环境变量互相矛盾"那一整类
问题就不存在了——比如把衰减窗口配得比锁的总时长还短，攻击者等一会儿就能自己解锁。

**口令错误（按 IP）**

| 连续失败次数 | 后果 |
| --- | --- |
| < 7 | 不锁，只是每次失败多等 400ms |
| 7 ~ 9 | 锁 1 分钟 |
| ≥ 10 | 锁 5 分钟；之后**每错一次都续 5 分钟** |

这张表**两条路由共用**（批改和口令页），因为爆破的人会走更松的那条。唯一的差别是清零点，
见下面那条。

- **输对口令立刻清零**失败计数（连同那把锁一起）——**前提是这一次是批改**。
  口令页验对了**不清零**（它借不到 `recordSuccess` 的语义，那一下会顺带吃掉一次额度），
  理由和代价在「访问口令」那一节末尾。
- **衰减**：1 小时内没有新的失败，失败计数就按 0 算（下一次失败从 1 重新数）。
- **总时长封顶**：一把锁从触发那一刻起最多持续 30 分钟。到顶后自动解锁**并清零失败计数**，
  重新给 10 次机会。见下面「关于锁定」。

**批改次数（按 IP）**：固定窗口，每小时 100 次（`REVIEW_RATE_LIMIT_PER_HOUR`，设 0 表示不限）。

### 计数口径

两道限制**各管各的**：口令猜错**不占用**那 100 次额度。计数发生在**口令校验通过之后**，
所以：

- 错口令 → 只记失败，不消耗配额（这正是"锁定顺带保护了用户自己的配额"那条推理失效的原因，
  见下面「关于锁定」）。
- 口令对但作文太短，被 `lib/review.ts` 的 `normalizeInput` 拒掉（400）→ **这一次已经计进去了**。
  也就是说计的是"口令通过的请求"，**不是**"真正调用了模型的请求"。别按后者的口径去理解配额。

### 关于锁定（这一段和上一版的结论相反）

上一版是纯内存的，所以 README 在这里写的是"两道都关掉的话对外的花费就没有上限了"，
并且论证过"锁定挡的是爆破，但它顺带保护了用户自己的配额，所以别关"。

**这两条现在都不成立了。** 计数和锁定都真的生效了（前提是配了 `DATABASE_URL`），
而且错口令不再消耗配额，所以那条"锁定保护配额"的推理链整个断掉。反过来说，
锁定现在有它自己的代价，那才是需要权衡的东西：

规则里"到 10 次之后，每错一次都锁 5 分钟"这句话单独看是有问题的。它的本意是挡死爆破，
但它同时是一件武器：**同一个出口 IP 下只要有一个人每 5 分钟打错一次，这个 IP 就被无限期锁死。**
校园网、宿舍、公司 NAT 这些场景下大量人共用一个出口 IP，受害者根本不知道自己是被谁连累的，
而且他输对口令也没用——锁定期内正确口令不能穿透（能穿透的话，锁就不再限制猜测速率了）。

30 分钟的总时长封顶就是这个的补偿：到顶后自动解锁并清零。攻击者仍然只能拿到
约 10 次猜测 / 30 分钟，而受害者最多等 30 分钟就能恢复。**这个取舍是刻意的**，
改封顶值之前先想清楚上面那条连锁反应。

### 失效模式（按危险程度）

1. **IP 标识的可信度全押在平台覆写 `x-forwarded-for` 上。**
   key 取自 XFF 链的第一项（`clientKeyFrom`），回落到 `x-real-ip`，再回落到 `"unknown"`。
   Vercel 会覆写 XFF，所以直连部署在 Vercel 上是可信的。但**前面只要再加一层代理**
   （Cloudflare、自建反代），第一项就可能是调用方自己写进去的——攻击者可以给每个请求
   换一个"新 IP"，整套限流立刻归零。所以代码**刻意不去优先信 `x-real-ip`**：万一平台
   不覆写它，自带一个 `x-real-ip` 头就能绕过一切。**部署之后请实测这条假设**
   （见下面「部署后验证」）。
2. **数据库挂了会降级，而降级是漏的。** 连不上数据库时**不会**变成"不限"——那等于在
   最需要限流的时候把限流整个抹掉。它会退回单实例的内存实现：站点照常能用，但多实例下
   会漏。这个降级是**响的**：终端里会打一条告警日志，`GET /api/review` 的 `persistence`
   字段会变成 `"memory"`，输入页上会出现一条黄色提示。看到任何一条都该去查数据库。
3. **按 IP 归并**，不是按设备。同一个出口 IP（校园网/宿舍/公司 NAT）共用配额和锁定，
   上面「关于锁定」讲的就是这个。这是刻意的取舍——用客户端可伪造的 cookie 做"设备"
   标识反而能被一键绕过（清 cookie 即重置），IP 才是防爆破的可信单位。
4. **固定窗口不是严格的上限。** "每小时 100 次"是固定窗口，在窗口边界处最坏允许 2 倍
   突发（这一小时的最后一次和下一小时的最早一次可以挨着发生）。所以对外说的是
   **"约 100 次/小时"**。真正的滑动窗口需要存时间戳序列，代价大得多。
5. **`unknown` 桶现在是个全局单点。** 所有取不到 IP 的请求共用同一个 100 次和同一把锁。
   Vercel 上不会出现（总会带上 XFF），自建的无代理环境会出现。

### 没配 `DATABASE_URL` 会怎样

限流退回**单实例内存**实现，也就是上一版的行为。本地开发无所谓；**线上没配就等于这道
限制基本不存在**，而页面和日志都会告诉你。建库三步见 `.env.local.example`。

### 数据库要花多少钱

Neon 免费档足够：一张表、每个见过的 IP 一行、每次请求一次 SELECT + 一条写语句。
陈旧行由机会性清理删掉（每约 1000 次请求清一次，删掉超过 24 小时没动过的行）——
**清理是必须的**：不清的话 IP 轮换（僵尸网络、IPv6）能把表撑爆，撑爆之后 Postgres 报错、
代码降级，限流又变成漏的。

清理**同时扫降级用的那个内存实现**，而且不是"只在数据库失败时才扫"。数据库故障期间
遭遇伪造 IP 洪泛的话，内存里每个假 IP 一条且永不释放；等数据库恢复之后，主实现每次都
成功，那条失败分支再也进不去，长驻进程（`next start` 自托管）里这些条目会一直留到
进程重启为止。两个实现每次一起扫，是为了让"降级"这个状态不留下只能靠重启收拾的尾巴。

超时设的是 4 秒（`lib/db.ts` 的 `DB_TIMEOUT_MS`）。这个值偏大是**故意**的：Neon 免费档
闲置约 5 分钟后会挂起，唤醒要 0.5–2 秒，而这个站点的流量正好是一阵一阵的，
冷启动是常态而不是异常。按"健康数据库"的延迟去调小，会让相当大一部分正常请求
被误判成故障、悄悄走降级。

## 请求体大小上限

`lib/request-body.ts` 把请求体硬性限制在 128 KB。这不是可选项：Next 的 App Router
route handler **没有**默认 body 上限（Pages API 那个 1MB 限制不适用于它），不设限的话
任何匿名请求都能让服务端先把任意大的 JSON 读进内存、解析完，之后才轮到口令校验——
闸门拦不住这一步。

限制是**流式计数**实现的，不只看 `Content-Length`：恶意客户端可以不带这个头、改用
分块编码。超限会立刻中断读取，不把剩下的读完。超过上限返回 413 `PAYLOAD_TOO_LARGE`。

## 页面与接口

| 路径 | 说明 |
| --- | --- |
| `/` | 首页（开播页）：表情包墙 + 花体英文标题 + 一个跳到口令页的按钮。纯静态、零 JS |
| `/access` | 口令页：首页那个按钮的落脚点，批改页唯一的前门。验过了才跳 `/review`。纯静态外壳 + 一个客户端表单 |
| `/review` | 作文输入页：题目、正文、目标档次、实时字数、示例填充。作文**自动存草稿**（刷新/被回收后能恢复），页首有「上次的报告还在」的入口；右下角有回到顶部的按钮 |
| `/result` | 结果展示页：档次、分数、总评、维度诊断、升档建议（含 before/after 改写示范）、证据溯源、训练区（按错误类别给的通用练法，没有就整节不显示）、原文批注（与证据卡双向跳转）。宽屏上**左原文、右批改**并排（见「报告页的两栏」），右下角有回到顶部的按钮。旧报告会标上生成时间。底部有「返回输入界面」（报告留着）和「批改另一篇」（报告清掉）两个不同的出口 |
| `POST /api/review` | 批改接口。入参 `{ essay, topic?, targetBandLevel?, accessCode? }`，返回 SSE 事件流（`REVIEW_STREAM=0` 时退化成一次性 JSON） |
| `GET /api/review` | 探活。返回 `{ ready, gated, model, persistence }`，输入页据此提前提示缺 key / 缺口令 / 限流没持久化 |
| `POST /api/access` | 口令页的校验接口。入参 `{ accessCode }`，只回答"这个口令对不对"。**不碰模型、不占批改额度**，但防爆破待遇和批改完全一致 |

输入限制：`essay` **只有下限 20 字符，没有字数上限**；`topic` 最多 1000 字符。
下限定义在 `lib/types.ts`，输入页和服务端用同一组数字。

作文不限字数是 2026-09 按用户要求改的，原来卡在 8000 字符。注意**真正的天花板并没有消失**，
它挪到了 `lib/request-body.ts` 的 128 KB 请求体上（折算约 12 万字符英文 / 4 万汉字 / 1 万个 emoji）。
那个数是按模型上下文窗口定的，所以只要请求体过得来，模型那边就不会因为超长而报错——
超长输入拿到的是一个正常的批改结果，不是一个看不懂的上游错误。详见那个文件的注释。

批改接口的错误码与状态码：

| 状态 | code | 含义 |
| --- | --- | --- |
| 400 | `INVALID_INPUT` | 入参不合法（空/过短/题目超长），或请求体不是 JSON |
| 401 | `INVALID_ACCESS_CODE` | 口令不对 |
| 413 | `PAYLOAD_TOO_LARGE` | 请求体超过 128 KB |
| 429 | `RATE_LIMITED` | 两个来源，文案不同：①「批改请求太频繁」= 这个 IP 当小时用满了 100 次；②「连续输错太多次」/「已锁定」= 口令连错 7 次或 10 次触发了锁定。**错口令不占那 100 次额度**，两道限制各管各的。带 `Retry-After` 头。被锁的请求连请求体都不会被解析（早拒在读 body 之前）。详见「限流的真实边界」 |
| 499 | `CLIENT_ABORTED` | 客户端主动断开，服务端一并中止了上游调用。这个码只出现在服务端日志里——断开的那一方已经不在了 |
| 500 | `MISSING_API_KEY` / `MISSING_ACCESS_CODE` | 服务端没配好，不是调用方的问题 |
| 502 | `UPSTREAM_ERROR` / `BAD_MODEL_OUTPUT` | 模型服务出错或输出不可解析 |
| 504 | `TIMEOUT` | 批改超时（总预算用尽，或长时间没有新内容） |

上面的状态码只覆盖**开流之前**就失败的情况。接口是流式的（见下一节），一旦开始返回
内容，状态码就固定成 200 了，后来的失败只能走带内 `error` 帧。

还有两个码**只会出现在客户端**，不经过这张表：`TIMEOUT`（首帧迟迟不来）和
`CONNECTION_LOST`（中途断连）。它们由 `lib/watchdog.ts` 在本地判定，见下面「客户端看门狗」。

`POST /api/access` 用的是**同一套 code 和状态码**，但它只可能出现 400 / 401 / 413 / 429 / 500
那几行——502 / 504 / 499 都是"调模型"这一侧才有的，它压根不调模型。

单次批改的总预算默认 100 秒（`REVIEW_TIMEOUT_MS` 可调）。这个默认值**刻意**比路由的
`maxDuration = 120` 少 20 秒：模型返回后还要解析输出、在原文里逐条定位证据、组织响应，
两者相等的话，模型掐着点返回时平台会先把函数掐掉，用户只看到一个平台级报错，
而额度已经花掉了。

这个预算**覆盖到读完响应体为止**，两条路都是（以前只有流式那条路做到了）：定时器不在
拿到响应头时就清掉，`await res.json()` 也在它的覆盖范围内。少了这一条，上游发完头就把
body 卡住时，非流式那条路（`REVIEW_STREAM=0`，README 推荐的逃生口）会一路挂到平台
120 秒掐断——用户看到的是平台级报错，**而额度已经烧了**。

另外多了一道 `REVIEW_STALL_MS`（默认 30 秒）：上游连续这么久没有吐出任何新字节就主动中止。
用户真正会遇到的失败几乎都是这一种，所以它单独有一个能说明白发生了什么的提示语，而不是
一个光秃秃的秒数。

**但这道停滞计时器要从生成开始才起算，不能从发请求就起算。** 上游首字节偶尔要等几十秒
（长 prompt 下不罕见），那段时间连接还在等响应头、一个字都还没开始吐——把它算成「30 秒
没有新内容」就会掐掉一次本来能成的批改，还报一条误导性的「超时」。所以计时器由调用方在
**响应头到达之后**才启动（`lib/deepseek.ts` 的 `openChatStream` 里那一次 `watch.kick()`）。

用户关掉标签页或刷新时，服务端会一并中止上游的模型调用，不再为一个没人接收的响应
继续计费（路由把 `request.signal` 透传到了 `chatJSON` / `openChatStream`）。

### 结果和草稿存在浏览器的哪里

**服务端不落库**：作文只在批改的那几十秒里经过服务端，之后它只活在浏览器里（`lib/store.ts`）。
存的是 `localStorage`，不是 `sessionStorage`——后者的生命周期就是「这个标签页」，而批改要等
几十秒，这期间手滑按到 Cmd/Ctrl+W、手机上切出去被系统回收，都不是小概率事件，一次就该白花的
批改（额度是花掉的，作文是写出来的，两样都补不回来）。

换来的代价有两条，**都在界面上明说了**，没有藏着：

- **报告会留在共用电脑上。** 所以 `/result` 对超过 24 小时（`RESULT_FRESH_MS`）的报告会加一句
  「这不是刚生成的报告」并印上生成时间，判定是纯函数 `isResultFresh`。报告**照常显示**——
  旧报告仍然有价值，没有理由因为旧就藏起来，只是不该让它冒充刚出炉的。
- **仍然不跨设备、不跨浏览器**，只是能跨标签页了。真要做分享，得改成服务端存储 + 短 id。

**还没提交的作文也留了一份草稿**，同一个 `localStorage`。它和结果是两回事：结果在服务端有过
一份权威副本，草稿只存在于这个浏览器里，丢了就真没了。存正文/题目/目标档次三个字段，防抖写入
（打字停下来才写一次），批改**成功**才删——失败要留着让人重试。

恢复**不自动发生**：页首弹一条提示，带着草稿的开头几十个字（免得你对着两份草稿猜哪份是哪份）
和「恢复它」/「丢弃」两个按钮。自动填回去的话，一个已经写完新作文的人一进页面就会被旧内容
盖掉——而他想不想要那份旧的，只有他知道。共用电脑上那份草稿更可能根本不是你写的。

⚠️ 提示还挂着的时候，**任何一次输入都会先把它撤掉**（`claimTyping`），否则防抖写入会拿
刚渲染出来的空字段把库里那份草稿覆盖掉——也就是"看见了提示但直接开始打字"的人会静默丢掉
那份草稿。这条改动改起来很容易踩，`components/EssayForm.tsx` 里写了「改了会怎样」。

`/result` 底部的「返回输入界面」也走这条路：它把这篇作文写回草稿再跳回 `/review`，
于是那边弹的就是上面那条提示，点「恢复它」就接着改。同页的「批改另一篇」是另一个意思——
它连报告一起清掉，回到一张空表单。

草稿有 16 万字符的上限（`DRAFT_MAX_CHARS`）：`localStorage` 是**同域共享配额**的，而访问口令
也存在这里，一篇误粘进来的巨型文本能把配额吃满，之后口令静默存不下——那个故障看起来跟草稿
毫无关系，极难排查。

`/review` 上还有一条低调的「这个浏览器上还有一份 X 时间生成的报告」入口。只有批改成功那一瞬间
的自动跳转能到 `/result`，少了这个链接，留下的报告就够不着了。放得低调是有意的：它是顺带告诉你
一声，不是这条流程的主线。

## 批改是流式的

`POST /api/review` 返回的是 SSE（`Content-Type: text/event-stream`），不是一次性 JSON。
报告在输入页上边生成边填出来，分数作为收尾出现——**一出现就是终值**。

事件白名单（定义在 `lib/types.ts` 的 `ReviewStreamEvent`）：

| 事件 | 载荷 | 时机 |
| --- | --- | --- |
| `meta` | `{ stats, model, topic, startedAt }` | 上游一打开就发。成功时第一个事件一定是它 |
| `summary` | 总评文本 | 模型把这个字段写完整之后 |
| `strengths` | 优点数组 | 同上 |
| `dimensionScores` | 维度诊断分（可能分几帧到） | 同上 |
| `evidence` | 一条引文，`{ pending: true, ... }`，**没有坐标** | 一条一帧 |
| `progress` | `{ chars }` | 2 秒定时，无条件发 |
| `result` | 完整 `ReviewResult` | 最后。到这一帧为止的渐进内容全部作废 |
| `error` | `{ error, code }` | 开流之后的任何失败 |

三条硬规矩：

- **帧里没有 `score15`，也没有 `warnings`。** 分数要过服务端的上限校正（依据模型自己
  标的 major 条数与维度分），提前露出模型的原始分会几秒后当场跳一次（13 → 12）；
  `warnings` 里那条「分数已由系统校正：模型给出 N 分」会把同一个数泄露出去。
  过滤在服务端做，不靠客户端自觉。
- **不回显 `essay`。** 客户端本来就有（渐进视图也不渲染原文批注），把原文回传一遍纯属浪费——
  而且现在作文不限字数，这份浪费的上限是 128 KB。
- **没有百分比。** 模型还要写多少字是未知的，画一个按时间爬的进度条是骗人。
  `progress` 报的是「已经收到多少字符」，不涨就是诚实的「上游确实没有新动静」。

### 客户端看门狗

读循环不是裸的 `reader.read()`。TCP 静默黑洞（对端不告而别，既没有 FIN 也没有 RST）下
`read()` 既不 resolve 也不 reject，而**服务端并不知道连接已经死了**——它照样每 2 秒往一个
没人收的 socket 里写心跳，一路写到自己的预算耗尽。那段窗口里用户看到的就是「已用 N 秒」
一直往上数、转圈、没有任何异常。所以要有一个客户端自己的读超时。

阈值只有**一份**，在 `lib/watchdog.ts`：`lib/use-review-stream.ts` 拿它真的掐请求，
`components/ReviewProgress.tsx` 拿它决定要不要提示。两边各写一份的话，迟早会出现
「提示说再等等、请求其实已经被掐了」这种自相矛盾的界面，而且只在慢网络上偶发。

| 阶段 | 阈值 | 为什么是这个数 |
| --- | --- | --- |
| 首帧之前 | 110 秒 | 这一段**没有存活信号**：上游返回响应头之前服务端一个事件都不发，于是「连接死了」和「正在正常等待上游」在客户端看来一模一样。既然分不清就不能猜，只能等服务端自己的总预算（100 秒）走完，再宽限 10 秒让它的报错先飞过来。设短了就是**误杀**——上游首字节偶尔会慢到几十秒，那种批改本来是能成的 |
| 首帧之后 | 40 秒 | 这一段有硬信号：服务端每 2 秒一个心跳，40 秒 = 20 个心跳一个都没到，不可能是「上游在长思考」（上游真卡住时心跳照发，而且服务端会在 30 秒时报错推下来）。留到 40 而不取 30，是为了让服务端那条**更具体**的报错先到达 |

沉默 20 秒（`SILENCE_HINT_SECONDS`）时先给一句安抚，**不判死**。这条「不哭狼」的边界比阈值
本身更容易被改坏：首帧之前完全正常的等待也可能有十几秒，那时弹一句"好像出问题了"只会让人
白紧张，然后过两秒内容就到了。

两种判死的文案不同，因为**用户能做的事不一样**：中途断连八成是网络（检查网络后重试），
首帧不来八成是上游排队（过一会儿重试通常就好）。含糊地说一句"超时了"会让人以为是自己的
作文有问题。中途断连的错误码是 `CONNECTION_LOST`，**故意不复用**服务端的 `TIMEOUT`——
语义是链路而不是上游，界面给的处理建议也不一样。这两个码是客户端自己造的
（`ReviewStreamError.code` 是 `string`，不像服务端那样受 `ReviewErrorResponse` 的联合类型约束）。

**哪些失败是真状态码、哪些走带内**，取决于失败发生在开流之前还是之后：

- **开流之前**（闸门、缺 key、上游 401/403/5xx、空内容）→ 照旧是真状态码，就是上面的
  错误码表。做法是**先打开上游、拿到响应头，再返回流**，所以这些错误还来得及变成
  `500` / `502`。代价是首字节要多等约 1 秒（上游的 TTFB），紧接着发出的 `meta` 帧让
  用户感觉不到。
- **开流之后**（生成中途上游挂了、总预算或停滞超时用尽、上游输出被截断）→ 只能走带内
  `error` 帧，此时 HTTP 状态码已经固定成 200。客户端把**已经收到的部分留在界面上**并给
  重试按钮——把已经花钱生成的 90% 扔掉是最差的选择。

客户端**按 `content-type` 分支**：不是 `text/event-stream` 就按一次性 JSON 处理。所以
`REVIEW_STREAM=0` 是一个运维逃生口——整个退回「一次请求一次返回」，客户端一行都不用改。
换到不支持流式的上游时也用它。

增量解析（`lib/json-stream.ts`）是**纯函数式全量重扫**：每收到一段 delta 就从零重扫整个缓冲，
而不是维护增量状态机。缓冲只增长，纯重扫天然幂等，也绕开了「chunk 边界正好切断 `\"`、
`A` 或代理对」这类经典失配。这里有一条要在代码里记住的安全性质：**最终结果永远是
`extractJson(累积全文)` 解出来的，不是扫描器的输出**——所以扫描器的 bug 最多让渐进视图
稀疏（少报），永远污染不了报告。

SSE 的响应头里 **`Cache-Control: no-transform` 是承重墙**，不是装饰：Next 15 默认给每个
请求套一层 compression，而它内置的 compressible 把 `text/event-stream` 判成可压缩，
阈值检查也不救场（流式响应没有 `Content-Length`）。加上 `no-transform` 让 `shouldTransform()`
直接返回 false，把压缩整个从链路上摘掉，不再依赖「Next 每次 `res.write` 后会调 `res.flush()`」
这个实现细节。

## 五个设计决定

### 1. 分数由模型给，档次由代码查表

学生看到的档次不是模型自己报的。模型只输出一个 0–15 的整数分，档次由
`lib/rubric.ts` 的 `bandForScore()` 按官方区间查出来。这样模型没法自创档位边界，
分数和档次永远自洽。折算到 106.5 分制也是纯算术。

模型输出一律当**不可信输入**处理，逐字段校验兜底，而这条路径上的静默出错特别难看：

- `score15` 走 `readScore15()`，不是无脑 `Number()`——`Number(true)` 是 1、`Number("")`
  是 0、`Number("0x10")` 是 16，`parseInt("12abc")` 是 12。数字和数字字符串之外的输入
  一律判 0，**并且记一条 warning**：模型把 12 写成 `"12"` 时，学生拿到的会是一份看起来
  完全正常、却显示 0 分 0 档的报告，无 warning 无报错。
- `kind`（亮点/小扣分/大扣分）不是三者之一时**保留条目**、降级成 `minor`，并标出
  `kindDegraded`（报告里那个徽章带 title 说明）。不丢弃是因为一条字段异常不该让整份
  已经花钱生成的批改作废；不静默是因为 `kind` 同时喂给展示（颜色）和判分（按 major
  条数的分数上限校正），静默降级会让一次字段异常同时污染两边——本该被压分的报告照旧
  发高分，而报告上看不出来。对比：`dimension` 非法是**整条丢弃**的，两者方向不同，
  是因为 `kind` 有安全的兜底值而 `dimension` 没有。

### 2. 四级是整体评分，所以维度分不计入总分

四级作文采用**整体评分法**：阅卷员看完全文凭整体印象给一个档次，而不是把几个维度
加起来。所以这个项目里 `score15` 是唯一的计分来源，内容/语言/结构三个维度分
**只用于显示强弱分布**，不参与总分。任何「内容 4 分 + 语言 3 分 + 结构 4 分 = 11 分」
的算法都是错的。报告里也写明了这一点。

### 3. 证据坐标不来自模型

「证据溯源」是这样做的：模型被要求从原文**逐字抄一段**，坐标由服务端在原文里
重新定位算出来（`lib/evidence.ts`）。

这么做是因为模型数不清第几个字符，但它抄得对原文。而且——

- 抄错了会被抓到：定位失败就是 `verified: false`，报告里明确标出「未能在原文中定位」，
  而不是画一个看起来精确、实际错位的下划线。
- 定位方式会一并返回：逐字命中 / 忽略大小写后命中 / 分段命中（引文含省略号）/
  模糊命中 / 未能定位。用户知道每条引用有多可信。
- **「找到了」和「找对了」是两件事，分开说。** 上面那条回答的是**怎么**匹配上的，
  它回答不了「命中的**是不是那一处**」——一条短引文（`he`、`I like sports`）在原文里
  出现两次时，取走第一处并返回「逐字命中原文」，报告就带着最可信的那个徽章高亮到**另一句**
  上面。这不是"抄错了"（那种会响亮地失败成 `verified: false`），而是**装作成功**，
  用户没有任何线索。所以定位还另外给一个歧义标记：`多处匹配（N 处）` / `近似匹配`，
  与定位方式**并列**显示而不是互相顶替（见 `lib/types.ts` 的 `AmbiguityReason`）。
  报告里那句「N/M 条已定位」照旧成立——歧义是 verifiedCount 的**子计数**，不是另一条分支。
- 同一句话被两条证据引用时，后一条会自动找下一处出现位置，不会两个高亮叠在一起。

**两个方向都能跳。** 点原文里的高亮跳到对应的证据卡，点证据卡上的「原文第 X–Y 字符」
跳回原文那一处，跳过去的那块由 CSS 的 `:target` 自己亮起来。用的是朴素的 `<a href="#...">`
加两个 id 前缀（`anchor-` / `card-`），不是 onClick——所以键盘和朗读器天然可用、浏览器
后退键能退回来，**而且导出的那份零 JS 报告里同样有效**。锚点得查 `lib/highlight.ts` 的
`anchorMap`，不能自己拼：重叠的证据会被合并进同一个高亮块，只有其中第一条能当上 id，
自己拼 `anchor-${id}` 会指向一个不存在的元素（两边都有注释钉着这一条）。

### 4. 升档建议必须给改写示范，而且示范要能被原文证伪

「把语言改好一点」这种建议，学生看完还是不知道改哪句。所以每条升档建议都带一个
`before` / `after` 改写示范：`before` 是原文里的原话，`after` 只改那一处
（整句重写就看不出是哪一处改动带来了提升）。

但**只强制会更糟**：模型给不出好例子时会**编一句原文里没有的话**，学生照着一条不存在的
「原句」去对照，比不给示范还坏。所以强制和核查是配对的——

- 服务端拿 `before` 回原文里重新定位（`locateExampleQuote`，见 `lib/review.ts`）；
- 定位不到 → 标 `exampleUnverified`，报告里明说「这个原句没能在原文中找到」，
  并追加一条 warning；
- 真的没给（纯结构类建议落不到某一个句子上）→ 标 `exampleMissing`，报告里用**中性**提示
  说明原因。这是正常降级不是故障，**不打 warning**。

⚠️ 判定条件是 `exact | normalized`，**不能退到 fuzzy**。`locateQuote` 的模糊匹配阈值是
词重叠 ≥80%，对一整条证据引文够用，对一句短示范毫无判别力：原文是
`I very like help other people`，模型编一句 `I like very`，三个词里中三个、重叠 100%，
会被判成「已验证」——正好是这个功能要抓的那种编造。`scripts/selftest.ts` 里有一条
专门钉住这个的回归断言。

### 5. 训练区是查表来的通用练法，不是模型现编的

报告结尾的「训练区」回答的是另一类问题：不是「这一篇哪里错了」，而是「我这种反复出现的
毛病，平时该怎么练」。做法是分工——

- **模型只诊断**：从 13 个受控类别（拼写 / 时态 / 主谓一致 / 中式英语 …）里挑出这篇
  最该练的 1-3 项，并说明**为什么是这篇**（必须引用本篇的具体现象，禁止「中国学生普遍…」）；
- **练法由服务端查表**（`lib/training.ts`）：每个类别配一段「写作时怎么做」+
  「平时怎么练」+「当心什么」。

这样练法文案零幻觉、措辞统一、可写断言，模型 token 增量也极小。代价是**同一类问题所有
学生看到的练法一样**——所以卡片上专门有一句「以下是「XX」这一类问题的通用练法，不是针对
你这一篇写的」，并用浅底容器把通用练法和模型给的那句诊断在**视觉上分开**。混在一起，
学生会以为「拼写要换会拼的词」也是模型读了他作文得出的结论。

写练法文案的原则是**写动作，不写态度**：「交卷前留 2 分钟倒着扫一遍拼写」可以，
「要细心」「多积累」一条都不收。13 个类别在 `scripts/selftest.ts` 里逐条断言非空、
条数下限和标签齐全——`Record<TrainingFocus, …>` 保证得了键齐全，保证不了内容是空的。

> 13 个类别里只有 8 个锚在评分标准上（5 个对应严重错误、3 个对应小错），
> `word-choice` / `sentence-variety` / `cohesion` / `paragraphing` / `task-response`
> 这 5 个是**新造的**，标准里没有对应说法。改 `lib/rubric.ts` 不会自动同步它们，
> 这一点在 `lib/training.ts` 的头注释里也写着。

## 界面：主题、动效、字体

风格是「奶油米白 + 薄荷绿」的柔和教育风，主色是**浅薄荷底配深青字**（不是饱和底色配白字）。
样式只有 `app/globals.css` 一份，组件里只用那里的 class，配色一律不写在行内——只有
「这是数据不是设计」的地方例外（维度条的宽度）。

**深浅主题**。顶栏右上角的开关在浅色与深色之间切换，选择记在 `localStorage.theme`；
没选过的人跟随系统 `prefers-color-scheme`。做法是 `app/layout.tsx` 的 `<head>` 里一段
**阻塞式内联脚本**（`lib/theme.ts` 的 `buildThemeScript()`），在浏览器首次绘制之前就把
`data-theme` 写到 `<html>` 上，所以刷新不会先闪一下白。CSS 侧只有 `:root[data-theme="dark"]`
一个深色选择器——脚本总会写上这个属性，不需要再维护一份 `@media` 的深色令牌副本，
也就不会有「两份深色值慢慢漂开」的问题。

代价是**无 JS 时只有浅色**。这个 app 没有 JS 本来就是个空壳（表单、fetch、localStorage、
流式读取全靠它），不值得为它维护第二份令牌。

**下载的报告始终是浅色**：它会被打印、会被转发、会脱离浏览器设置单独存在，跟着开关变深色
只会在纸上变成一片黑。报告里的 `color-scheme` 也写死 `light`，否则深色系统的浏览器会把
滚动条和表单控件画成深色，贴在奶油底上很脏。

> 报告样式（`lib/report-html.ts` 的 `REPORT_CSS`）是网页样式的**平行副本**，有自己的类名。
> 改 `globals.css` 的令牌值时记得把那张表也改一遍，否则下载下来会比网页旧一个版本。

**字体**：标题和正文都是系统无衬线栈，只有英文正文和引文用衬线（`--font-serif`）。

刻意**不引任何 webfont**：拉丁衬线的收益太小，代价是每次构建都依赖外网；中文衬线更不能引
——Google 的 CJK 字体按 unicode-range 切成几十个分片，`next/font` 对它的子集元数据是错的
（vercel/next.js#53522），会把所有分片都拖下来。而 Windows 上中文衬线只能回落到宋体，
那是另一种风格（老门户那种）。真想做得和参考站一样，正确做法是用 `pyftsubset` 把标题那
几十个字切成一个子集 woff2 自己托管。

**动效**（都写在 `globals.css` 里，没有引任何动画库）：

| 动效 | 触发 |
| --- | --- |
| 上移淡入 | 滚动进场（首页 hero、结果页各大节）。`components/Reveal.tsx`，IntersectionObserver，只动一次 |
| 悬浮抬升 / 按下 | 按钮、证据卡、升档建议卡的 hover 与 `:active` |
| 落定 | 最终分数出现时缩放 + 淡入一次 |
| 生长 | 维度条从 0 长到它的值（`@keyframes grow`，行内 width 就是终点） |
| 骨架微光 | 等待界面还没到的文本块 |
| 浮出 | 回到顶部按钮：滚过一屏才淡入。`components/BackToTop.tsx`，`/review` 和 `/result` 各挂一次（输入页挂在页面上而不是表单里——等待视图会把表单整个换掉，按钮不能跟着消失；报告页挂在"有报告"那一支上，另外两支短得滚不动） |
| 背景光晕漂移 | `body::before`，22 秒一来回 |

三条约束，改动时别破：

1. **分数不做数字滚动。** 滚动会短暂显示 0→4→9 这些不是终值的中间数。这个 app 里
   「显示出来的数字永远是真的」——所以分数是一次性落定，不是滚上去的。
2. **不出现百分比 / 进度条。** 总量未知，按时间爬的进度条是骗人。骨架微光不是进度——
   它的长度固定，不随已收到的字符数变化。
3. **滚动进场不用在流式视图里。** `ReviewProgress` 每个 SSE 帧都在替换子节点，进场动画
   会被反复重放，看起来像页面在抽搐。它只服务于 `/result` 和首页。

无 JS 时内容必须可见：进场动画的隐藏态挂在 `html[data-reveal-ready]` 上，由脚本在首帧前
写上——脚本没跑就不会藏，不会出现整页空白。系统开了**「减少动态效果」**（`prefers-reduced-motion`）
时所有位移和动画都关掉，内容完整显示。

### 报告页的两栏（宽屏）

`/result` 在 ≥1280px 时是左右并排：**左边原文、右边批改**（`.report-layout` 的网格）。
原来的顺序是"证据列表 → 原文批注"，核对一条证据得先滚下去、再滚回来找原文，
这条改动就是为了掐掉那两段滚动。左栏跟着页面停住（`position: sticky`）并且自己能滚，
所以整篇原文始终在视线里。

容器封顶 960px（左右各 20px 内边距），所以两栏宽度是**固定的 360 + 26 间隙 + 534**，
跟窗口多宽没关系——断点只决定"拆不拆"。

四个决定值得写下来，改的时候容易踩：

- **DOM 顺序是「批改在前、原文在后」，视觉顺序是反的。** 靠显式 `grid-column` 换位。
  这么排是因为窄屏读的就是 DOM 顺序：先看多少分、该改什么，想深究再往下看原文——
  这也正是分栏之前那一版的行为，所以手机上没有任何变化。代价是键盘 Tab 和朗读器
  跟着 DOM 走，先过批改再走过原文（批改是主内容，这样是对的）。
- **整块 CSS 只挂在 `@media screen and (min-width: 1280px)` 上。** 于是**打印和
  导出的 HTML 报告都天然是单栏**，不需要在 `@media print` 里再摊平一次。
  那种"屏幕写一份、纸上再写一份"的写法最容易漏掉一半，症状是纸上只印出侧栏的第一屏。
  门槛定在 1280px 是为了让 1000~1280 这一档（小笔记本）保住单栏那份宽敞。
- **左栏宽度钉死 360px，不按比例分。** 它是参照物：窗口再宽，正文的行宽也不变，
  视线不用每次重新找位置。代价是两样：右栏只剩 534px，而左栏自己的行宽
  （360 减掉内边距后约 40 字符）比常规的 45~75 偏窄——这是拿行宽换右栏宽度的取舍，
  想反悔就改 `grid-template-columns` 那个 `360px`，只此一处。
- **右栏的两处断点是在这里重写的。** `.scoreboard` 和 `.dims` 的断点按**视口**写
  （720 / 860），而右栏只有 534px，比它们设想的最窄情况还窄，那两个断点永远不触发：
  分数板两列的下限加起来正好 534px（和右栏一样宽，一点余量都没有），所以直接单列；
  维度卡改成 `auto-fit`，让栏宽自己决定几列（534px 时是 2 列、每张 261px）。

⚠️ 左栏那条 `.report-aside-scroll` 上的 `min-height: 0` **不能删**。flex 子项的默认
最小高度是内容高度，少了它 `overflow` 不生效，侧栏会照着作文长度把整页撑长——
症状是"分栏看起来生效了，但滚到一半左栏就跑没了"。另一个是 `max-height` 那个视口封顶：
不封的话长作文的底部一截永远滚不出来（sticky 元素高过视口时，贴着的那部分够不着）。

### 首页（开播页）

`app/page.tsx` 是个玩笑页：花体英文标题 + 300 个猫贴纸铺满背景，一个按钮进 `/access`（口令页）。
整页**零 JS**，是服务端渲染的静态 markup，没有水合这一步，所以首屏不会先白一下。
五条实现上的讲究：

- **猫贴纸是自己画的，不是网上下的表情包。** 六个 `<symbol>` 定义在 `components/MemeCats.tsx`，
  造型照着"圆头耄耋"那个梗的辨识点（炸开的飞机耳、怒眼、张嘴哈气），但一笔一笔都是原创。
  不直接用那个梗的网图有两个原因，都写在那个文件的注释里：**那个梗的原始素材在公开讨论里
  被判为疑似虐猫**（猫被关着、被激怒摆姿势、被拖把戳），九阳豆浆、《1999》外服、王者荣耀
  国际服都因为用它被炎上过，而这个站是要挂公网的；另外网图是位图，颜色写死、放大就糊，
  矢量贴纸的颜色能跟着深浅主题翻转。**所以这版只有猫，没有笼子、拖把、棍子**——那些道具
  才是问题所在。
- **表情包墙是 CSS grid，不是 `background-image`**。背景图得先知道视口多大，或者要切一张正好
  拼得上的图；grid 的 `auto-fill` 是自动铺满的。贴纸数量在组件里**写死**（300 个，按 5K 屏
  倒推），量视口就得等客户端、首屏会白一下；多出来的被 `overflow` 裁掉，不占版面。
- **贴纸顺序是写死的，不用随机数**。随机会让服务端和客户端渲染出两套 DOM，轻则闪一下、
  重则水合报错。每个贴纸的角度/大小/透明度由 7 条 `:nth-child` 规则轮转给出，颜色另按 4 格
  一轮、猫另按 6 格一轮；**7、4、6 两两互质**，所以"这只猫 + 这个角度 + 这个颜色"要 84 格
  才撞一次，看不出排版的规律。
- **视线中心压了一层底色渐隐**（`.landing::before`），猫只在四周清楚。这是"清新"的关键：
  标题怎么都读得清，也就不需要给文字加底板。
- **整墙只挂一个动画**（`.meme-wall` 的缓慢漂移），不是每张贴纸各自浮动——300 个各自动画
  就是 300 个合成层，为这点抖动不值得。

贴纸的绘制有三条硬约束，改坐标前先看 `components/MemeCats.tsx` 的文件头注释：耳朵必须有一个
角扎进脑袋圆内（脑袋是后画的、会盖住耳朵，底角在圆外就会留一条缝，整墙的猫看起来"耳朵浮着"）、
胡须必须从脑袋外缘起笔且用猫自己的颜色、五官必须落在圆内且后画的嘴不能盖住先画的鼻子。

`MemeCats.tsx` 是服务端组件，六个 `<symbol>` 只存一份，300 个格子全靠 `<use>` 引用——所以
生产构建里 `/` 的 HTML 是 103 KB 原始 / **9.7 KB gzip**，JS 仍然是 162 B。

花体英文用的是**系统字体栈**（`--font-script`），没有引 webfont，理由和 `--font-serif` 一样。
所以字形跟着操作系统走：Windows 上是 Segoe Script / Ink Free，macOS 上是 Snell Roundhand，
Linux 上 `cursive` 由系统决定、可能不是花体。想固定成一种，往 `public/fonts/` 放一个子集
woff2 再加一条 `@font-face` 即可。

**换成自己的图片**：`components/MemeCats.tsx` 的 `MEME_IDS` 和 `app/page.tsx` 的循环是全部逻辑。
把 `public/memes/` 建起来放图（`public/` 目前还没有），数组元素改成 `/memes/xxx.png`，把
`<span className="meme">` 换成 `<img className="meme" src={...} alt="" />`（`alt=""` 别省：
这层是装饰，读出来只会烦人），再给 `.meme` 补 `width: 100%; height: 100%; object-fit: contain;`。
`MEME_IDS` 的**长度最好保持和 7 互质**，否则某个角度会永远配到同一只猫，排版的规律就露出来了。

## 换成你自己的批改标准

如果你拿到了真正的 `english-exam-writing-reviewer` Skill，只需要改 **`lib/prompt.ts`**
里的 `buildReviewPrompt()`——把 SKILL.md 的规则搬进去，让它继续返回 `{ system, user }`
两个字符串即可，其余代码一行都不用动。

前提是模型输出的 JSON 结构保持不变（结构定义在 `lib/prompt.ts` 的 `JSON_CONTRACT`，
解析与校验在 `lib/review.ts`）。如果你的 Skill 要求的输出字段不一样，改这两处：

1. `lib/types.ts` — 调数据类型定义
2. `lib/review.ts` 里的 `parseEvidence` / `parseDimensionScores` / `parseUpgradePlan` — 对应的解析

档次表和折算规则在 `lib/rubric.ts`，改完记得把 `RUBRIC_VERSION` 往上加一位，
报告页脚会显示这个版本号。

**升版不只在改评分时。** 只要**输出契约**变了就要升，哪怕一个分数的算法都没动——
`meta.rubricVersion` 是存在旧报告上的唯一一个契约版本戳，不升版就分不清一份报告是
按哪套契约生成的。`2024.2` 就是这么来的：本轮要求每条升档建议都给 `example`、
并新增了 `trainingPlan`，判分逻辑一行没改。

## 换成别的模型

`lib/deepseek.ts` 用的是原生 `fetch` 打 OpenAI 兼容接口，没有引 SDK。改 `.env.local`：

```bash
DEEPSEEK_BASE_URL=https://api.moonshot.cn/v1   # 或通义、智谱、本地 Ollama
DEEPSEEK_MODEL=moonshot-v1-8k
DEEPSEEK_API_KEY=...
```

前提是对方兼容 `/chat/completions` 和 `response_format: { type: "json_object" }`，
以及 `stream: true` 的 SSE 输出（不用给 `stream_options`）。不兼容的话，模型可能返回带
Markdown 代码块的 JSON——`extractJson()` 有三层兜底，但如果对方连字段都不按
`JSON_CONTRACT` 来，就得改 `lib/review.ts` 的解析。

如果对方根本不支持流式，把 `REVIEW_STREAM=0` 设上——接口退回一次性 JSON，
等待界面仍然可用，只是报告在最后一次性出现。

## 部署

Vercel 上要配的环境变量：`DEEPSEEK_API_KEY`、`REVIEW_ACCESS_CODE`，以及**`DATABASE_URL`**。
前两个不配的后果（页面会明说）见上面「访问口令」；`DATABASE_URL` 不配的后果见
「没配 `DATABASE_URL` 会怎样」——站点照常能用，但限流退回单实例内存。

建表用 `npm run db:init`（本地跑，指向线上那个库），或者把 `db/schema.sql` 粘进
Neon 控制台的 SQL Editor。全表都是 `IF NOT EXISTS`，重复跑没事。

### 部署后验证

这几条是本地验不了、只能上线后实测的，**第一条尤其重要**：

1. **`x-forwarded-for` 是不是真的被平台覆写了。** 整套限流的可信度全押在这上面
   （见「失效模式」第 1 条）。做法：带一个伪造的头发请求，看配额桶有没有跟着变。

   ```bash
   # 连着发两次，第二次把 XFF 换成别的值。
   # 如果第二次又是一个新桶（看 rate_limits 表里多出一行不同的 client_key），
   # 说明平台**没有**覆写这个头 —— 那么这套限流在公网上是可绕过的，要尽快换成
   # 平台提供的可信来源（比如 Vercel 的 request.ip 或它注入的专用头）
   curl -s -o /dev/null -X POST https://你的域名/api/review \
     -H 'content-type: application/json' \
     -H 'x-forwarded-for: 1.1.1.1' \
     -d '{"essay":"...","accessCode":"..."}'
   ```

2. **数据库真的在写。** 打几次批改（含一次错口令），然后
   `SELECT * FROM rate_limits` 里应该看得到自己那一行，`window_count` 在涨。

   顺便验一下口令页那条路：打一次**错**口令应该拿到 401（不是 200，也不是 404——
   404 说明这条路由没部署上去），而 `window_count` **不该动**。

   ```bash
   curl -s -o /dev/null -w '%{http_code}\n' -X POST https://你的域名/api/access \
     -H 'content-type: application/json' -H 'x-forwarded-for: 1.1.1.1' \
     -d '{"accessCode":"definitely-wrong"}'
   ```
3. **降级是响的。** 故意把 `DATABASE_URL` 改错重新部署一次：站点仍能用，
   终端里有一条明显的告警，`GET /api/review` 的 `persistence` 变成 `"memory"`，
   输入页出现黄色提示。验证完记得改回去。

## 已知限制

- **限流同时依赖两件外部的事**：平台的 `x-forwarded-for` 覆写（见「失效模式」第 1 条
  和上面的部署后验证），以及数据库活着。两件都有对应的人工检查步骤，但没有自动告警。
- **锁定期内正确口令不能穿透**。被同一个出口 IP 连累的人只能等——最多 30 分钟。
  这是「锁」这个概念的必然代价，详见「关于锁定」。
- **输入框的描边对比度低于 WCAG 1.4.11 的 3:1**。这是柔和风格的自觉代价：把边框加深到
  3:1 会让整页变成一堆框。补偿是**焦点环**——键盘焦点用的是高对比的深青描边加一圈浅薄荷，
  比默认的浏览器焦点环明显得多，所以 Tab 走一遍始终看得见自己在哪。
- **等待界面上没有分数，也没有百分比**。这是刻意的，不是没做完：总量未知，画一个按
  时间爬的进度条是骗人；分数要等上限校正算完，提前露出会当场跳变。见上面「批改是流式的」。
- **渐进视图没有原文批注**。某条引文的高亮坐标取决于整批引文（`lib/evidence.ts` 按长度
  排序并互斥占位），证据没到齐之前那个坐标根本不存在，硬画只会画出会移动的下划线。
  所以高亮只在 `/result` 出现。定位本身是毫秒级的 CPU 活，不拖慢收尾。
- **中途失败时已经生成的那部分不落盘、也不进导出报告**。它只在界面上留着供你看一眼，
  点重试就是重新批一次——上游的额度已经花掉了。
- **报告会留在共用电脑上。** 存 `localStorage` 是「误关标签页就白花一次批改」的对价，
  界面上的补偿是给旧报告盖上生成时间，但挡不住下一个人打开这一页。见上面
  「结果和草稿存在浏览器的哪里」。
- **结果和草稿都不跨设备、不跨浏览器**（同一个浏览器里现在能跨标签页了，以前不能）。
- **草稿是"这台浏览器"的，不是"每个人"的。** 共用电脑上那句恢复提示可能恢复出别人写的
  作文，所以它旁边有一个「丢弃」。也因为它和访问口令共用 `localStorage` 配额，
  草稿额外有一个长度上限（撑爆配额的症状是"口令静默存不下"，跟草稿看不出关系）。
- **口令页和批改页的失败计数是同一个。** 所以"在口令页连错 6 次、第 7 次输对"之后再错一次
  就会被锁——口令验对了不清零（理由见「访问口令」）。这是刻意的取舍，不是漏掉的分支。
- **`quote` 依赖模型抄得准**。抄错了虽然会被标成「未能定位」而不会静默出错，
  但那条证据就废了。`buildReviewPrompt` 里用了一大段硬性要求在压这个风险。
  另一头是短引文的多处匹配：那种情况标成「多处匹配（N 处）」，**仍然是绿的**——
  它不是错误，只是不够确定，用户对着原文自己能判断该是那一处。
- **分数仅供参考**。整体评分法本身有主观性，不同模型给的分数会有差异，
  不代表真实考试成绩。报告页脚也写了这句。
